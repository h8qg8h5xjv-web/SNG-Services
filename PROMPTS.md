# Промпты для Claude Code

Единый порядок выполнения. Копируй по одному, следующий — только когда предыдущий доведён до конца и `npm run build` проходит.
После каждого шага: `git add -A && git commit -m "..."`.

Файлы в корне репозитория: `CLAUDE.md` (правила работы), `DESIGN.md` (требования к интерфейсу и данным), `PROMPTS.md` (этот файл).

## 1. Схема базы данных

```
Спроектируй и создай полную схему БД. Миграции клади в /supabase как пронумерованные .sql файлы. Сгенерируй TypeScript-типы в /types.

Таблицы:

- categories — 14 категорий из DESIGN.md. Названия на ru и en, slug, имя иконки Tabler, порядок сортировки
- languages — справочник языков обслуживания из DESIGN.md. Код ISO 639-1, название на родном языке. Английского в справочнике нет
- providers — бизнес или мастер. name_en и description_en обязательны, категория, borough, адрес, координаты, телефон, telegram, instagram, сайт, slug, статус draft / published
  - fulfillment_type: not null, check constraint на native_booking / external_order / enquiry
  - external_order_url: text, nullable. Обязателен, если fulfillment_type = external_order
  - НЕ заводи отдельное поле booking_enabled: оно дублировало бы fulfillment_type, а два источника правды однажды разойдутся
- provider_languages — связь многие-ко-многим providers и languages
- provider_translations — provider_id, locale, name, description
- services — услуга провайдера. Название, описание, длительность в минутах, цена в пенсах, capacity по умолчанию 1
- schedules — недельное расписание: день недели, время начала, время конца
- schedule_exceptions — конкретная дата, закрыто целиком или другие часы
- bookings — ссылка на service, начало и конец, party_size по умолчанию 1, имя, телефон, email, статус pending / confirmed / cancelled, is_visible_to_group по умолчанию false
- events — афиша по схеме из раздела 2а DESIGN.md

Требования:
- snake_case, множественное число
- время в timestamptz, UTC
- цены целыми числами в пенсах
- внешние ключи с продуманным ON DELETE
- индексы под запросы: провайдеры по категории и borough, брони по провайдеру и диапазону дат, события по starts_at
- констрейнт: провайдер со статусом published обязан иметь минимум один язык
- защита от переполнения слота на уровне БД: сумма party_size подтверждённых броней не может превысить capacity услуги
- constraint: расписание и брони допустимы только при fulfillment_type = native_booking
- RLS включена везде. Публично читаются только published-провайдеры, их услуги и опубликованные события. Брони читает только владелец записи и админ. Запись — только сервисная роль или админ

Объясни в резюме, как именно реализована защита от переполнения слота.
```

## 2. Интернационализация

```
Прочитай раздел 1 DESIGN.md.

- next-intl, базовая локаль en, префикс в URL всегда явный
- локали: en, ru, uk, kk, ka, hy. Больше не заводи. Внимание: kk казахский, ka грузинский, в конфиге рядом с кодом держи название
- переводы в /messages/{locale}.json, исходные строки на английском
- отсутствующий ключ падает на английский, никогда не показывай сырой ключ
- конфиг локалей с флагом enabled, в переключателе только включённые
- заполни en и ru полностью. Для uk, kk, ka, hy создай файлы с полной структурой ключей и английскими значениями, enabled false
- редирект с корня по Accept-Language, иначе на /en. Выбор в cookie перебивает заголовок
- hreflang для всех включённых локалей плюс x-default на en
- переключатель языка в шапке
- все тексты только через переводы, никаких строк в компонентах

Язык интерфейса и язык обслуживания — разные сущности, не смешивай.
```

## 3. Тестовые данные

Файл `seed-data.json` лежит в корне. Данные вымышленные, заменяются на настоящие позже.

```
Возьми seed-data.json из корня проекта и напиши сид-скрипт.

- сначала categories (14 штук из DESIGN.md) и languages (справочник из DESIGN.md)
- потом провайдеры из seed-data.json со всеми услугами и языками
- каждому провайдеру сгенерируй недельное расписание: будни с 10:00 до 19:00, суббота с 11:00 до 17:00, воскресенье выходной. Паре провайдеров сделай нестандартное расписание и по одному schedule_exception, чтобы было на чём тестировать слоты
- события: дата считается как сегодня плюс days_from_now
- координаты подставь примерные по borough, это демо
- всё создавай со статусом published, кроме двух провайдеров — их оставь в draft, чтобы было видно, что фильтр по статусу работает

Картинки:
- фото не загружай, используй URL плейсхолдеров: https://picsum.photos/seed/{image_seed}/800/600 для провайдеров и /1200/630 для событий
- добавь picsum.photos в remotePatterns в next.config, иначе next/image их не отдаст
- поле для картинки должно принимать и внешний URL, и путь в Supabase Storage. Когда придут настоящие фото, менять код не должно понадобиться

Скрипт идемпотентный: повторный запуск обновляет, а не дублирует. Команда npm run seed.
```

## 4. Каталог

```
Реализуй публичный каталог по разделу 3 DESIGN.md: главная, страница категории, страница провайдера.

- фильтра по языку нет: ни чипов на главной, ни фильтра в категории, ни параметра в URL
- на странице провайдера языки показываются некликабельной справочной строкой
- категории без опубликованных провайдеров на главной не показываются
- порядок плиток по числу опубликованных провайдеров
- блок «Свободно сегодня» пока заглушка, живые данные подключим после шага 7. Пометь это в коде
- поиск по названию и описанию, регистронезависимо, с поддержкой кириллицы
- при отсутствии перевода описания показывай английский, без пометки
- поведение по fulfillment_type:
  - native_booking: кнопка «Записаться»
  - external_order: кнопка «Order on {название площадки} ↗», ведёт на external_order_url в новой вкладке, rel="noopener noreferrer". Никакого календаря и слотов. Цены не показываем вообще
  - enquiry: кнопки нет, показываем контакты
- тип виден на карточке в списке до клика, чтобы человек понимал, останется он у нас или уйдёт наружу
- server components где возможно, запросы к Supabase только через /lib
- mobile-first от 375px, пустые состояния, скелетоны, тач-цели от 44px, иконки Tabler
```

## 7. Слоты и бронирование

```
Расчёт слотов и бронирование.

Расчёт:
- на вход id услуги и дата
- недельное расписание провайдера на этот день недели
- применяем schedule_exceptions
- вычитаем занятость: слот занят, когда сумма party_size подтверждённых и ожидающих броней достигла capacity услуги
- режем на слоты по длительности услуги
- прошедшие по времени слоты не показываем

Логику вынеси в /lib отдельной функцией. Юнит-тесты обязательны: обычный день, выходной, день с исключением, день с одной бронью посередине, групповая услуга с частичным заполнением, границы интервалов.

Бронирование:
- /[lang]/[category]/[slug]/book — услуга, календарь на 30 дней, слоты, число человек, контакты
- без регистрации, статус pending
- переполнение ловится констрейнтом БД, ошибку показывай понятным текстом
- страница подтверждения
- если у провайдера booking_enabled false — кнопки записи нет, показываем контакты

После этого подключи живые данные в блок «Свободно сегодня» на главной.
В админке — список броней с фильтром по дате и провайдеру, смена статуса.
```

## 10. Фундамент под платное продвижение

Саму рекламу не запускаем. Делаем только то, что дорого добавлять задним числом.

```
Подготовь фундамент под платное продвижение. Саму рекламу НЕ реализуй.

1. Единая функция ранжирования:
   - вынеси всю логику сортировки провайдеров в /lib/ranking.ts,
     функция rankProviders(providers, context)
   - context: категория, фильтры, локаль
   - сейчас внутри обычная релевантность и сортировка
   - все места, где сейчас есть ORDER BY по провайдерам, должны ходить через неё
   - оставь в сигнатуре место под будущий boost, но не реализуй его

2. Лог событий, новая таблица provider_events:
   - provider_id, event_type (impression / click / booking_started / booking_completed)
   - position (позиция в списке на момент показа), surface (home / category / search)
   - session_id — псевдонимный, из cookie, не привязан к личности
   - occurred_at, category_id, locale
   - индексы под агрегацию по provider_id и дате
   - НЕ храни IP и user-agent. Для статистики они не нужны, а под GDPR это лишние
     персональные данные

3. Сбор:
   - impression пишется при показе карточки в списке, батчем, не по одному запросу
   - click при переходе на страницу провайдера
   - booking_started и booking_completed в потоке брони
   - всё асинхронно, ошибка логирования никогда не ломает страницу пользователю

4. Простая агрегация в админке: показы, клики, CTR и брони по провайдеру за период.

В резюме объясни, как устроен батчинг показов и почему он не бьёт по производительности.
```

Когда дойдёт до самой рекламы: платное размещение по DMCC Act 2024 обязано быть явно помечено плашкой, видимой до клика, плюс строка в правилах площадки о том, что оплата влияет на выдачу. Буст работает только внутри релевантной выдачи, не больше одной проплаченной карточки на экран.
