# Категории и интерфейс

## 1. Два языка — разные сущности

| | Язык интерфейса | Язык обслуживания |
|---|---|---|
| Что это | На каком языке приложение говорит с пользователем | На каком языке говорит бизнес |
| Где живёт | Файлы переводов, cookie, префикс URL | Колонка в таблице `providers` |
| База | Английский | — |
| Список | en + языки СНГ | Только языки СНГ |
| Роль | Выбор пользователя | Условие попадания в каталог |

**Базовый язык интерфейса — английский.** Он же язык исходных строк в коде и язык, на который падает откат, если перевод отсутствует.

Локали интерфейса: `en` (база), `ru`, `uk`, `kk`, `ka`, `hy`. Шесть штук, список закрыт.

Названия в переключателе — на родном языке: English, Русский, Українська, Қазақша, ქართული, Հայերեն.

Осторожно с кодами: `kk` — казахский, `ka` — грузинский. Отличаются одной буквой, перепутать легко, и ошибка тихая — страница просто отдаёт не тот язык. В конфиге локалей рядом с кодом держи комментарий с названием, а в сиде и тестах проверяй оба явно.

Почему именно эти. Критерий не размер общины, а «сколько людей в ней не читают по-русски свободно». Русский — общий язык почти для всех выходцев из СНГ, поэтому он первый. Украинский нужен не по численности, а потому что значительная часть аудитории русский не выберет принципиально. Грузинский и армянский — самые заметные общины Лондона из оставшихся, и у них ниже всего покрытие русским среди тех, кому до сорока. Казахский добавлен решением владельца продукта: охвата почти не даёт, но работает на позиционирование площадки как общей для СНГ, а не только русской.

Остальные языки не делаем. Если позже понадобятся — это один JSON-файл, а не переделка.

Правила:

- новая локаль = один JSON-файл в `/messages`. Никаких изменений в компонентах. Добавление языка не должно быть задачей на разработку;
- **отсутствующий ключ падает на английский, а не показывает пустоту или сам ключ.** Это обязательно, иначе недопереведённая локаль ломает экран;
- в переключателе видны только локали с флагом `enabled` в конфиге. Локаль включается, когда переведена полностью, а не наполовину;
- URL: `/en/...`, `/ru/...` и так далее. Префикс всегда явный, включая английский;
- редирект с корня — по заголовку `Accept-Language`, если язык браузера есть в списке, иначе на `/en`. Выбор запоминается в cookie и перебивает заголовок;
- на каждой странице теги `hreflang` для всех включённых локалей плюс `x-default` на английский.

### Язык обслуживания

**Фильтра по языку в интерфейсе нет.** Весь каталог по определению состоит из бизнесов, обслуживающих на языках СНГ. Это и есть смысл площадки, отдельно фильтровать нечего.

Список: русский, українська, беларуская, қазақша, oʻzbekcha, кыргызча, тоҷикӣ, türkmençe, azərbaycanca, հայերեն, ქართული, română.

Английского в этом списке нет намеренно. Английский — это база интерфейса, а не признак бизнеса. Мастер, который говорит только по-английски, для этой площадки не подходит.

**Правило каталога: у каждого провайдера минимум один язык СНГ.** Это не фильтр, это условие публикации. Проверяется в двух местах: валидация в админке и констрейнт в БД, чтобы нельзя было опубликовать провайдера без языков. Провайдер без языка не может получить статус `published`.

Поле остаётся в базе именно ради этого правила — без данных о языках его нечем проверять. Плюс на странице провайдера языки показываются справочной строкой, чтобы человек видел, поймут ли его. Но это подпись, а не элемент навигации: ни чипов на главной, ни фильтра в категории, ни параметра в URL.

В базе — отдельная таблица `languages` (код по ISO 639-1, название на родном языке) и связь многие-ко-многим с `providers`. Не массив строк: иначе справочник расползётся по опечаткам, а констрейнт на публикацию будет не на что опереть.

### Контент провайдеров

Интерфейс переводится файлами. Описания бизнесов — нет, их пишешь ты.

- `name_en` и `description_en` обязательны. Это база, на неё падает откат;
- переводы описаний — таблица `provider_translations` (provider_id, locale, name, description). Заполняется по мере сил;
- если перевода на локаль пользователя нет — показывается английский, без пометки «перевод отсутствует». Пометка только в админке, чтобы ты видела пробелы.

## 2а. Афиша — отдельная сущность, не категория

События (концерт, стендап, вечеринка, выставка, детский спектакль, языковой митап) не помещаются в модель провайдера. Провайдер — это тот, кто работает по расписанию каждую неделю. Событие происходит один раз в конкретную дату и потом исчезает.

Если запихнуть афишу в `providers`, получится таблица с половиной пустых колонок и расписанием, которое ничего не расписывает. Поэтому — отдельная таблица.

```
events
  id, slug
  title_ru, title_en
  description
  category            -- концерт, стендап, вечеринка, выставка, дети, спорт, нетворкинг
  starts_at           -- timestamptz
  ends_at             -- timestamptz, nullable
  venue_name, address, lat, lng, borough
  price_from_pence    -- nullable, null = бесплатно
  ticket_url          -- внешняя ссылка, свои билеты пока не продаём
  organizer_provider_id -- nullable, ссылка на providers, если организатор есть в каталоге
  languages           -- на каком языке мероприятие
  cover_image
  status              -- draft / published
```

Правила:

- прошедшие события скрываются автоматически по `starts_at`, а не руками;
- билеты пока не продаём, ведём по `ticket_url` наружу. Свои платежи — отдельный проект с юридическим хвостом;
- поле `organizer_provider_id` связывает афишу с каталогом: у ресторана на его странице показываются его же события;
- афиша — главный источник повторных заходов. Каталог человек открывает раз в три месяца, афишу — каждую неделю.

## 2б. Что не так с бронированием ресторанов и спорта

Модель `services` рассчитана на «услуга фиксированной длительности одному человеку». Для маникюра это верно, для ресторана — нет.

Ресторан бронируют на количество человек, а вместимость ограничена столами, не временем мастера. Это другая математика доступности.

Групповые занятия в спорте — та же проблема: у слота есть вместимость, и на него записываются несколько человек.

Решение на Фазу 1: у `services` появляется поле `capacity` (по умолчанию 1) и у брони — `party_size`. Слот занят, когда сумма `party_size` подтверждённых броней достигла `capacity`. Это покрывает и групповые тренировки, и простую бронь столика.

Полноценная схема столов, залов и посадок — не сейчас. Ресторан, который не хочет брони, публикуется как листинг с контактами и без кнопки записи. Поле `booking_enabled` у провайдера.

## 3. Экраны

**Главная**
- шапка: город (пока только Лондон, но поле оставить) + переключатель языка интерфейса
- поиск одной строкой, ищет по мастерам, услугам и районам
- сетка категорий 4×2 плюс «Ещё»
- блок «Свободно сегодня» — провайдеры с открытыми слотами на ближайшие часы. Это главный крючок возврата, не «новые» и не «популярные»
- блок «Недавно смотрели» — из localStorage, без авторизации

**Категория** `/[lang]/[category]`
- фильтры: borough, цена, свободно сегодня или на этой неделе. Фильтра по языку нет
- сортировка: по релевантности, по цене, по ближайшему свободному слоту
- карточка провайдера: фото, название, район, диапазон цен, ближайший слот

**Провайдер** `/[lang]/[category]/[slug]`
- галерея, описание, список услуг с ценами и длительностью
- языки обслуживания — справочной строкой, некликабельной
- часы работы, карта, контакты
- кнопка брони закреплена внизу экрана на мобильном

**Бронирование** — три шага: услуга, дата и время, контакты. Без регистрации. Аккаунт предлагается уже после подтверждения.

**Афиша** `/[lang]/events`
- лента по датам: сегодня, завтра, эти выходные, дальше
- фильтры: категория события, borough, цена
- карточка: обложка, дата и время, название, место, цена от
- страница события: описание, карта, кнопка наружу за билетами, ссылка на организатора, если он есть в каталоге
- на странице провайдера — блок «Ближайшие события» из его же афиши

**Нижняя навигация**: Главная, Афиша, Записи, Профиль. Поиск живёт на главной, отдельный пункт ему не нужен. Четыре пункта, не больше.

## 4. Принципы интерфейса

- Mobile-first буквально: макет рисуется под 375px, десктоп — растянутая версия, а не наоборот.
- Кириллица длиннее латиницы примерно на 15%. Названия категорий в одно слово, кнопки тестировать на самом длинном языке.
- Никаких попапов с просьбой зарегистрироваться до первой брони.
- Пустое состояние в каждой категории и в каждом фильтре: что показать, если ничего не нашлось. Это отдельная задача, а не «потом добавим».
- Скелетоны вместо спиннеров.
- Тач-цели минимум 44px.

## 5. Социальные функции

### Фаза 2 — участники занятия

Закрывает сценарий «кто ещё ходит к этому тренеру» без пользовательского контента.

- у брони поле `is_visible_to_group`, по умолчанию `false`;
- на странице группового слота — участники, у которых флаг включён: имя и аватар, без контактов;
- «вы были на этом занятии вместе N раз» — считается из истории броней;
- ничего написать нельзя. Только присутствие.

Люди не публикуют контент, поэтому профиль риска по Online Safety Act принципиально другой, чем у чата. Показать юристу всё равно нужно, но это несопоставимые вещи.

### Фаза 3 — чат под провайдером

**Не автосоздание.** Чат появляется, когда у провайдера накопилось минимум 10 подтверждённых броней от разных людей. До этого кнопки нет. Иначе получаются сотни пустых комнат, а пустая комната выглядит как заброшенный проект.

Обязательные условия, без которых чат не запускается:

- **никакой анонимности.** Верифицированный аккаунт: подтверждённый email и телефон. Без установленной личности автора теряется защита оператора площадки по s.5 Defamation Act 2013, и ответчиком по иску о клевете становишься ты;
- **писать может только тот, у кого была подтверждённая бронь у этого провайдера.** Читать — все;
- хранение данных автора и IP на срок, достаточный для процедуры уведомления и ответа;
- кнопка жалобы на каждом сообщении и процедура рассмотрения обращений;
- очередь модерации в админке, удаление сообщения и блокировка пользователя;
- terms of service и правила сообщества, опубликованные до первого сообщения;
- оценка рисков нелегального контента, оформленная документом, до запуска;
- решение по детским обязанностям: либо сервис не для детей и это заявлено, либо выполняются детские обязанности с проверкой возраста. Категория «Дети» делает этот вопрос обязательным, а не теоретическим.

Пока хоть один пункт не сделан — чат не включается. Это не перестраховка: обязанности по нелегальному контенту применяются ко всем регулируемым user-to-user сервисам независимо от размера.

Ни один из этих пунктов Claude Code не придумает сам. Их надо задать явно.

### Жизненный цикл чата

Чат не живёт вечно. Состояния:

| Состояние | Условие | Что видно |
|---|---|---|
| `locked` | меньше 10 подтверждённых броней от разных людей | кнопки чата нет |
| `active` | последнее сообщение меньше 30 дней назад | чат открыт |
| `dormant` | последнее сообщение больше 30 дней назад | чат скрыт, кнопки нет |
| `purged` | прошло 12 месяцев в `dormant` | сообщения физически удалены |

Правила:

- **`dormant` — это не удаление, а скрытие.** Сообщения остаются в базе. Причина не сентиментальная: пока действует срок исковой давности по клевете и пока может прийти запрос по процедуре жалоб, история и данные авторов должны существовать. Удалив переписку в день скрытия, ты остаёшься без доказательств ровно тогда, когда они нужны;
- активностью считается только новое сообщение. Просмотры не считаются, иначе чат никогда не заснёт;
- если человек с подтверждённой бронью пишет в `dormant` чат — он мгновенно возвращается в `active`, история видна целиком. Порог в 10 броней заново не проверяется, он проходится один раз;
- физическое удаление через 12 месяцев `dormant` — отдельной задачей, с логированием факта удаления. Точный срок стоит уточнить у юриста: тут сталкиваются GDPR (не хранить дольше необходимого) и обязанности по OSA и защите от исков (хранить достаточно);
- сообщения, на которые была подана жалоба, из `purge` исключаются до закрытия обращения.

Техническая деталь, важная для реализации. `dormant` — **вычисляемое** состояние, а не колонка, которую кто-то проставляет. У чата есть `last_message_at`, и статус выводится из него прямо в запросе. Никакой фоновой задачи для скрытия не нужно: задача, которая раз в сутки бегает по всем чатам и меняет флаг, — это лишний механизм, который однажды не отработает и оставит данные в неверном состоянии. Фоновая задача нужна ровно одна — физическое удаление, потому что это единственное действие, которое нельзя вывести из запроса.
