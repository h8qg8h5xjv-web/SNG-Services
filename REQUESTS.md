# Заявки — модель рассылки

Дополняет `DESIGN.md`. Читать вместе с ним.

## 1. Зачем

Мастер не ведёт у нас расписание — он уже ведёт его в другом месте и второе вести не будет. Поэтому расписание мы не спрашиваем. Мы задаём один вопрос: «свободен ли ты вот тогда» — и мастер отвечает кнопкой.

Клиент предлагает окна времени. Мастер, принимая, выбирает конкретное время внутри окна. Его нажатие и есть обращение к его настоящему календарю.

Расписание остаётся опцией: кто его ведёт, у того бронируют мгновенно, без ожидания ответа.

## 2. Два типа заявки

| | `fixed` | `quote` |
|---|---|---|
| Категории | красота, обучение, спорт, дети, здоровье частное, питомцы | дом, переезд, праздники, авто |
| Цена | из прайса мастера, известна заранее | мастер называет в отклике |
| Ответ мастера | Беру / Не могу | предложение с ценой |
| Результат | автобронь по первому «Беру» | клиент выбирает из откликов |
| Бюджет клиента | только в режиме «любой мастер» | обязателен или рекомендуется |

Тип задаётся на категории (`categories.default_request_type`), не выбирается клиентом.

### Два режима внутри `fixed`

**Конкретный мастер.** Клиент выбрал Анну в каталоге. Заявка уходит только ей, цена — из её прайса. Отказ или молчание → предлагаем разослать похожим.

**Любой мастер.** «Нужен маникюр завтра утром». Рассылка всем подходящим, у которых разные цены. Здесь клиент задаёт потолок, иначе автобронь невозможна: неизвестно, на какую цену он согласен.

---

## 3. Окна времени, а не точное время

Точное время отсекает почти всех: в 9:00 занято, в 10:00 свободно — мастер просто откажется.

- клиент выбирает окна: «сегодня после 18:00», «завтра утром 9–12», «в выходные»;
- можно отметить несколько, минимум одно;
- в интерфейсе показываем зависимость: одно окно — ответ обычно за час, три окна — за 15 минут;
- мастер при принятии выбирает конкретное время внутри окна;
- клиент получает подтверждение с точным временем.

## 4. Схема

```
requests
  id, public_ref            -- короткий код для писем и бота
  customer_id               -- nullable, гостевые заявки разрешены
  type                      -- fixed | quote
  category_id
  service_id                -- nullable, только fixed + конкретный мастер
  target_provider_id        -- nullable, режим «конкретный мастер»
  borough
  address                   -- nullable, раскрывается только после матча
  description
  budget_max_pence          -- nullable
  status                    -- draft | broadcasting | matched | confirmed
                            -- | expired | cancelled | completed
  contact_name, contact_phone, contact_email
  created_at, expires_at

request_windows
  request_id, starts_at, ends_at

request_targets             -- кого спросили и в какой волне
  request_id, provider_id, wave, channel, notified_at
  response                  -- pending | accepted | declined | no_response
  responded_at

request_offers              -- только type = quote
  request_id, provider_id, price_pence, message, proposed_start
  status                    -- open | withdrawn | chosen | rejected

request_matches             -- единственный победитель
  request_id, provider_id, service_id
  starts_at, ends_at, price_pence
  booking_id
```

## 5. Волны и таймауты

| Волна | Когда | Кому уходит |
|---|---|---|
| 1 | сразу | категория + borough + в бюджет + активен + не на паузе |
| 2 | +15 мин | соседние borough |
| 3 | +15 мин | бюджет +25%, с пометкой «выше бюджета клиента» |
| — | +15 мин | `expired`, клиенту предлагаем расширить вручную |

Фильтр по бюджету мягкий: в третьей волне спрашиваем и тех, кто дороже. Мастер решает сам, клиент часто готов доплатить за подходящего.

Волны запускает фоновая задача — здесь она нужна по-настоящему, в отличие от «спящих» состояний, которые вычисляются из данных.

---

## 6. Гонка при принятии

Двое жмут «Беру» одновременно — выиграть должен один.

```sql
update requests
   set status = 'matched'
 where id = :request_id
   and status = 'broadcasting';
```

Ноль обновлённых строк = опоздал. В боте отвечаем «заявку уже забрали», без ошибки и без раздражения.

Создание `request_matches` и брони — в одной транзакции с этим апдейтом.

---

## 7. Дисциплина исполнителей

«Беру» — обязательство, а не интерес. Без последствий модель разваливается: клиент получает подтверждение и никого не получает.

Считаем по каждому провайдеру:

- доля принятых от полученных;
- медианное время ответа;
- отмены после принятия;
- неявки (проставляет админ).

Правила: две неявки — отключение от рассылки. Три отмены после принятия за месяц — понижение приоритета в первой волне.

Цифры внутренние, публично не показываем.

## 8. Канал уведомлений — приложение

> **TODO (реализовано частично).** Канал уведомлений сейчас — заглушка `ConsoleChannel` (`lib/notifications/`): печатает письмо в консоль сервера и ничего не отправляет. Точки вызова расставлены по-настоящему (волны 1/2/3, матч, отмена), факт отправки пишется в `request_targets.notified_at`/`channel`. Email (Resend) подключим, когда будет свой домен — как подключить, см. README → «Уведомления». SMS и push — той же абстракцией позже.

Заявки приходят мастеру **в приложение**, push-уведомлением. Приложение — единственное место, где мастер работает с заявками. Мессенджеры не используем: канал, который заменяет приложение, не даёт приложению появиться.

**Основной канал.** Push в мобильном приложении. Нажатие на уведомление открывает заявку с кнопками «Беру» / «Не могу» / «Другое время».

**Резервный канал.** Email и SMS для тех, кто ещё не установил приложение или у кого push отключён. В письме — не сама заявка, а ссылка в веб-кабинет, где те же кнопки. Это важно для холодного старта: первую заявку мастер получит до установки, иначе цепочка не замкнётся.

**Веб-кабинет как мост.** `/[lang]/business` открывается с телефона в браузере и работает без установки. Мастер приходит по ссылке из письма, отвечает, и уже там видит предложение поставить приложение, чтобы получать заявки быстрее.

Логика выбора канала:

- есть активный push-токен → push, дублирование по email через 5 минут без ответа;
- нет токена → email сразу, SMS через 5 минут;
- SMS платная — только для заявок первой волны и только тем, у кого доля ответов выше среднего.

Контакты клиента и адрес **не попадают ни в один канал**. Раскрываются только победителю после матча.

В `request_targets.channel` пишем фактический канал: `push` | `email` | `sms`.

## 9. Ориентир по цене вместо ползунка

Ползунок бюджета тянет рынок вниз: цифра на экране становится точкой отсчёта, большинство ставит у нижней границы, хорошие мастера перестают проходить и уходят.

Вместо этого показываем факт: «Уборка 3 часа в Croydon: обычно £60–85».

- перцентили 10 и 90, не минимум и максимум — иначе один демпингующий новичок растянет диапазон;
- считать по сопоставимым услугам: категория × borough × близкая длительность. Трёхчасовая уборка и генеральная в один котёл не идут;
- показывать только при 5+ ценах в выборке. Меньше — не показывать ничего;
- поле бюджета необязательное, с подписью «можно не указывать».

## 10. Деньги

**Stripe Connect, direct charges с `application_fee_amount`.** Именно эта схема, не destination charges.

- продавец — сам бизнес, деньги идут на его аккаунт Stripe;
- наша комиссия удерживается автоматически;
- площадка не держит средства ни секунды, вопрос о хранении чужих денег не возникает;
- возвраты делает бизнес, потому что он и есть продавец.

Берём **только booking fee**, остальное — напрямую бизнесу.

Списываем в момент подтверждения матча, не при создании заявки.

Политика возврата booking fee — написать до первой оплаты, не после первого спора:

- мастер отменил → возвращаем полностью;
- клиент отменил более чем за 24 часа → возвращаем;
- клиент отменил позже → не возвращаем;
- никто не пришёл и это не выяснено → решает админ вручную.

**Повторные обращения.** Клиент нашёл репетитора и ходит к нему год — эти сделки мы теряем, и запрещать бессмысленно. Рамка: мы берём деньги за знакомство, не за отношения. Первая заявка платная, дальше свободно.

Регулярные занятия — отдельная возможность: продавать не право на контакт, а удобство (автоплатёж, напоминания, перенос в два клика). Тогда остаются потому, что проще.

## 11. Что видит клиент, пока ждёт

Экран ожидания — половина продукта. Не спиннер, а состояние.

- «Спрашиваем 6 мастеров. Обычно отвечают за 12 минут»;
- по мере волн: «Расширили поиск на соседние районы»;
- матч: «Анна свободна завтра в 10:30, £30» + кнопка подтверждения;
- истечение: что делать дальше — шире окна, шире район, выше бюджет. Не тупик.

Обновление статуса — Supabase Realtime на строке заявки.

## 12. Промпты

### 12.1 Схема и логика

```
Прочитай REQUESTS.md. Реализуй модель заявок, шаг 1 из 3: данные и логика.
Интерфейс и бот — следующими шагами, сейчас не трогай.

1. Миграции: requests, request_windows, request_targets, request_offers,
   request_matches по разделу 4. Плюс categories.default_request_type
   и providers.broadcast_paused_until.

2. RLS:
   - клиент видит только свои заявки (по customer_id или по гостевому токену)
   - провайдер видит только те заявки, где он есть в request_targets
   - провайдер НЕ видит контакты и адрес до матча — вынеси их так,
     чтобы это обеспечивалось политикой, а не фильтрацией в коде
   - админ видит всё

3. Подбор исполнителей — чистая функция в /lib/requests/match.ts:
   вход — заявка и номер волны, выход — список provider_id.
   Правила волн из раздела 5. Юнит-тесты на каждую волну и на пустой результат.

4. Принятие заявки — атомарно, по разделу 6. Апдейт по условию status,
   создание match и booking в одной транзакции. Тест на гонку:
   два параллельных принятия, выигрывает ровно одно.

5. Фоновая задача продвижения волн и истечения. Идемпотентная:
   повторный запуск не рассылает дважды.

6. Статистика провайдера: доля принятых, медиана времени ответа,
   отмены после принятия. Вьюха или материализованная вьюха, не колонки.

В резюме объясни, как реализована защита от гонки и как проверил её тестом.
```
